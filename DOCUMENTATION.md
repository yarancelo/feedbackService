# Документация: сервис анонимной обратной связи

Полное описание того, как устроен и как работает каждый сервис системы. Документ
дополняет `README.md` (там — краткий старт) и объясняет внутреннее устройство:
слои, потоки данных, обработку ошибок, логирование и тесты.

---

## 1. Обзор

Система решает одну задачу: дать сотрудникам возможность **анонимно** оставлять
отзывы, а администратору — просматривать и модерировать их. Анонимность
обеспечивается тем, что при создании отзыва не собирается и не сохраняется никакая
информация об авторе: в таблице отзывов есть только тема, текст и время.

Приложение состоит из четырёх изолированных контейнеров, каждый со своей ролью, и
запускается одной командой `docker compose up --build`.

---

## 2. Архитектура

```
                         ┌───────────────────────────── docker network: appnet ─────────────────────────────┐
   браузер               │                                                                                   │
      │  HTTP :80         │    ┌──────────┐         ┌──────────┐          ┌──────────┐        ┌────────────┐  │
      └──────────────────►│───►│  proxy   │────/───►│ frontend │          │ backend  │───────►│  postgres  │  │
                          │    │ (nginx)  │──/api──────────────────────► │ (FastAPI)│        │  (PG 18)   │  │
                          │    └──────────┘         └──────────┘          └──────────┘        └────────────┘  │
                          │        :80                   :80                  :8080               :5432        │
                          └───────────────────────────────────────────────────────────────────────────────────┘
   наружу открыты: 80 (proxy) · 8080 (backend, для тестов) · 5432 (postgres, для ручной работы)
```

### Контейнеры

| Сервис     | Образ                 | Роль                                                           |
|------------|-----------------------|----------------------------------------------------------------|
| `proxy`    | `nginx:alpine`        | Обратный прокси: единственная точка входа для браузера         |
| `frontend` | сборка → `nginx:alpine` | Отдаёт статику собранного React-SPA                          |
| `backend`  | `python:3.14-slim`    | REST API (FastAPI), бизнес-логика, миграции                    |
| `postgres` | `postgres:18-alpine`  | Хранилище; генерирует `uuidv7()` и `now()` на своей стороне    |

### Ступенчатый запуск

Порядок старта задан через healthcheck'и и `depends_on … condition: service_healthy`:

1. `postgres` поднимается и проходит `pg_isready`;
2. только после этого стартуют `backend` и `frontend`;
3. `proxy` стартует последним, когда `backend` и `frontend` стали healthy.

Так к моменту приёма первого запроса вся цепочка гарантированно готова.

### Сеть и порты

Все контейнеры включены в bridge-сеть `appnet` и обращаются друг к другу по именам
сервисов (`postgres`, `backend`, `frontend`). Наружу проброшены только три порта:
`80` (браузер), `8080` (прямой доступ к API для тестов), `5432` (ручная работа с БД).

## 3. Жизненный цикл запроса

**Создание отзыва (публично).** Браузер → `POST /api/feedbacks` → `proxy` пробрасывает
на `backend` → контроллер валидирует тело через pydantic-схему → сервис создаёт
доменную модель → репозиторий делает `INSERT` (id и время проставляет БД) → сессия
коммитится → ответ `201` с готовым отзывом.

**Вход администратора.** `POST /api/auth/login` → контроллер → `AuthService`
сверяет логин/пароль через репозиторий → при успехе `security` выпускает JWT на 30
минут → ответ `200 {access_token}`; при неудаче поднимается `InvalidCredentialsError`
→ обработчик исключений превращает её в `401`.

**Просмотр отзывов (админ).** `GET /api/feedbacks?...` с заголовком
`Authorization: Bearer …` → зависимость `get_current_admin` декодирует токен и
загружает админа → сервис считает страницу (50 на страницу, фильтры и сортировка по
дате) → ответ со списком и метаданными пагинации.

**Удаление (админ).** `DELETE /api/feedbacks/{id}` → сервис ищет отзыв; если нет —
`FeedbackNotFoundError` → `404`; если есть — репозиторий удаляет → `204`.

## 4. Backend

### 4.1. Структура

```

│   └── versions/0001_initial.py
├── src/feedback_app/

│   ├── core/               # инфраструктура (не содержит бизнес-правил)
│   │   ├── config.py        # настройки из окружения
│   │   ├── logging.py       # настройка логгера + фабрика логгеров
│   │   ├── database.py      # engine, session factory, Base
│   │   ├── security.py      # выпуск/проверка JWT
│   │   ├── exceptions.py    # иерархия доменных исключений
│   │   └── dependencies.py  # DI: сессия БД, сборка сервисов, guard админа
│   ├── models/             # M (MVC): ORM-модели домена
│   │   ├── user.py

│   │   ├── auth.py
│   │   └── feedback.py
│   ├── repositories/       # уровень данных: доступ к БД, без исключений
│   │   ├── user_repository.py
│   │   └── feedback_repository.py
│   ├── services/           # бизнес-логика: правила, поднимает исключения
│   │   ├── auth_service.py
│   │   └── feedback_service.py
│   └── controllers/        # C (MVC): маршруты + перевод исключений в HTTP
│       ├── auth_controller.py
│       ├── feedback_controller.py
│       └── error_handlers.py

    ├── conftest.py          # фейки и фикстуры
    ├── unit/
    └── integration/
```

### 4.2. Слои и принципы

Код разбит на слои с **односторонней зависимостью** (сверху вниз):

```
controllers  →  services  →  repositories  →  БД
     │              │
   schemas        models
     │
   (перевод исключений в HTTP)
```

- Каждый модуль отвечает за одно. Функции и методы делают ровно одно действие;
  уровни абстракции не смешиваются (контроллер не знает про SQL, репозиторий не
  знает про HTTP).
- Зависимости передаются снаружи (dependency injection): сервис получает
  репозиторий в конструкторе, контроллер получает сервис через `Depends`. Благодаря
  этому каждый слой тестируется в изоляции с подставными зависимостями.

### 4.3. core — инфраструктура

**config.py.** Класс `Settings` (pydantic-settings) читает переменные окружения:
`DATABASE_URL`, `JWT_SECRET`, `JWT_ALGORITHM`, `JWT_EXPIRE_MINUTES`, `LOG_LEVEL`.
Единственная ответственность — предоставить типизированные настройки.

**logging.py.** Две маленькие функции: `configure_logging(level)` один раз
настраивает корневой логгер (идемпотентно, повторный вызов ничего не добавляет) и
`get_logger(name)` выдаёт именованный логгер модулю. Используются все уровни: DEBUG
(детальный ход), INFO (значимые действия), WARNING (ожидаемая аномалия — неверный
пароль, просроченный токен), ERROR/EXCEPTION (непредвиденные сбои).

**database.py.** Создаёт `engine`, фабрику сессий `SessionLocal` и декларативный
`Base`. Чистая инфраструктура, без правил.

**exceptions.py.** Иерархия доменных исключений:

```
AppError
├── AuthError                  → 401
│   ├── InvalidCredentialsError  «Неверный логин или пароль»
│   ├── TokenError               «Недействительный или просроченный токен»
│   └── AdminNotFoundError       «Администратор не найден»
└── NotFoundError              → 404
    └── FeedbackNotFoundError     «Отзыв не найден»
```

Каждое исключение несёт готовое сообщение и однозначно отображается в HTTP-статус.

**security.py.** `create_access_token(subject)` подписывает JWT с полями `sub`, `iat`,
`exp` (срок — 30 минут). `decode_access_token(token)` проверяет подпись и срок и
возвращает `sub`; при любой проблеме библиотечная ошибка **не** утекает наружу — она
оборачивается в доменную `TokenError`.

**dependencies.py.** Точки сборки для FastAPI:
- `get_db()` — сессия на время запроса: коммит при успехе, **откат при любом
  исключении**, закрытие в `finally`. Именно здесь выполняется требование «сброс
  транзакции при исключении».
- `get_auth_service`, `get_feedback_service` — собирают сервис поверх репозитория
  поверх текущей сессии.
- `get_current_admin` — извлекает Bearer-токен, отдаёт его `AuthService.identify`,
  который возвращает админа или поднимает `AuthError`.

### 4.4. models — слой Model

`User` (логин, пароль, id) и `Feedback` (id, тема, текст, время). Оба поля `id` имеют
`server_default = uuidv7()`, а `Feedback.created_at` — `server_default = now()`. Это
значит: Python **никогда** не задаёт эти значения — их вычисляет БД. После вставки
репозиторий перечитывает объект, чтобы получить сгенерированные значения.

### 4.5. schemas — слой View

pydantic-модели описывают одновременно валидацию входа и форму ответа (для JSON-API
«представление» — это и есть форма сериализованных данных):
- `LoginRequest` — логин и пароль обязательны и непусты.
- `FeedbackCreate` — тема и текст обязательны; валидатор обрезает пробелы и отвергает
  пустые строки (это и есть серверная защита «нельзя создать отзыв без темы/текста»).
- `FeedbackOut`, `FeedbackPage` — форма ответа и метаданные пагинации.

### 4.6. repositories — уровень данных

Единственный слой, который **не поднимает** доменные исключения: методы возвращают
значения или `None`. Смысл «не найдено» присваивается выше, в сервисе.

- `UserRepository`: `get_by_login`, `get_by_id`.
- `FeedbackRepository`: `add` (вставка + перечитывание сгенерированных БД полей),
  `get_by_id`, `delete`, `count`, `list` (окно с limit/offset, фильтры дат,
  направление сортировки). Арифметика страниц здесь **не** делается — репозиторий
  отдаёт «сырые» данные (элементы + общее число), а расчёт числа страниц живёт в
  сервисе. Так уровни абстракции не смешиваются.

### 4.7. services — бизнес-логика

Здесь живут правила, и именно здесь ошибки выражаются исключениями.

- `AuthService`
  - `authenticate(login, password)` — возвращает админа или поднимает
    `InvalidCredentialsError` (сравнение пароля — открытым текстом, по требованию).
  - `login(...)` — аутентифицирует и возвращает подписанный токен.
  - `identify(token)` — раскрывает токен в админа (`TokenError` /
    `AdminNotFoundError` при проблемах).
- `FeedbackService`
  - `create(topic, body)` — создаёт доменную модель и отдаёт её в репозиторий.
  - `list_page(page, date_from, date_to, newest_first)` — считает `total` и число
    страниц (`ceil(total / 50)`) и собирает `FeedbackPage`.
  - `delete(id)` — удаляет либо поднимает `FeedbackNotFoundError`.

### 4.8. controllers — слой Controller

Тонкие функции-маршруты. Они не содержат бизнес-логики и **не** ловят ошибки через
`try/except`: вызывают сервис и позволяют исключению «всплыть».

`error_handlers.py` регистрирует один обработчик `AppError`, который по типу
исключения выбирает HTTP-статус (`AuthError → 401`, `NotFoundError → 404`, иначе
`500`) и возвращает `{"detail": …}`. Пятисотки логируются как ERROR, ожидаемые
доменные ошибки — как DEBUG. Так обработка ошибок исключениями работает сквозным
образом на всех уровнях, кроме уровня данных.

### 4.9. main — точка сборки

`create_app()` в одном месте: настраивает логирование, создаёт FastAPI, добавляет
CORS, регистрирует обработчики исключений и подключает маршруты под префиксом `/api`
(включая `/api/health` для healthcheck).

## 5. База данных и миграции

- Таблицы создаются **только** миграциями Alembic (`0001_initial`), не автосозданием.
- `id` обеих таблиц — тип `UUID` со `DEFAULT uuidv7()`; `created_at` отзывов —
  `TIMESTAMP WITH TIME ZONE` со `DEFAULT now()`. Оба значения генерируются **на
  стороне PostgreSQL** — это встроенные функции PG 18.
- Есть уникальность `login` и индекс по `created_at` (ускоряет сортировку/фильтры).
- Первая миграция засевает одного администратора `admin` / `password`, чтобы система
  была работоспособна «из коробки».
- При старте контейнера `backend` выполняется `alembic upgrade head` — команда
  идемпотентна и применяет только ещё не применённые миграции. Это и есть требование
  «последняя миграция применяется при перезагрузке сервиса, если не применена ранее».

## 6. Frontend

### 6.1. Структура

```
frontend/
├── src/
│   ├── main.jsx            # точка входа + маршрутизация (react-router)
│   ├── api/               # общение с backend
│   │   ├── client.js        # request(): заголовки, разбор ответа, ApiError
│   │   ├── auth.js          # login
│   │   └── feedback.js      # create / list / delete + buildQuery
│   ├── lib/               # чистые утилиты
│   │   ├── logger.js        # уровневый логгер (debug/info/warn/error)
│   │   ├── token.js         # хранение access-токена
│   │   └── datetime.js      # форматирование времени
│   ├── hooks/             # состояние и логика экранов
│   │   ├── useAuth.js       # вход/выход, признак авторизации
│   │   └── useFeedbackList.js # пагинация, фильтры, загрузка, удаление
│   ├── components/        # переиспользуемые презентационные компоненты
│   │   ├── Field.jsx
│   │   ├── Button.jsx
│   │   └── ErrorBanner.jsx
│   ├── pages/
│   │   ├── FeedbackForm.jsx  # публичная форма
│   │   └── Admin/           # экран администратора
│   │       ├── index.jsx     # выбирает Login или List по авторизации
│   │       ├── LoginForm.jsx
│   │       └── FeedbackList.jsx
│   └── styles/index.css
└── tests/                 # vitest + testing-library, на уровне src
```

Разделение то же по духу, что и на бэкенде: **api** (транспорт) → **lib** (чистые
функции) → **hooks** (состояние) → **components/pages** (отображение). Компоненты не
знают, как устроены HTTP-запросы; они работают через хуки и api-модули.

### 6.2. Как работает

- `api/client.js` — ядро транспорта. `request()` собирает заголовки (при `auth: true`
  добавляет `Authorization: Bearer …`), разбирает тело, а при не-2xx поднимает
  `ApiError` с полем `status` и человекочитаемым сообщением (в т.ч. разворачивает
  массив ошибок валидации pydantic). Каждый запрос логируется на уровне DEBUG, ошибки
  — ERROR.
- `hooks/useAuth.js` — держит признак `authed`, метод `login` (сохраняет токен) и
  `logout` (чистит токен).
- `hooks/useFeedbackList.js` — вся логика списка: страница, сортировка, диапазон дат
  (даты преобразуются в границы `T00:00:00` / `T23:59:59`), загрузка, удаление. При
  ответе `401` (истёк 30-минутный токен) вызывает `onUnauthorized`, что выкидывает на
  экран входа.
- `pages/FeedbackForm.jsx` — публичная форма. Кнопка отправки заблокирована, пока не
  заполнены обе поля (клиентская проверка вдобавок к серверной). После успешной
  отправки показывает подтверждение — фирменный «конверт положен в ящик».
- `pages/Admin/*` — вход и список. При неверных данных показывается «Неверный логин
  или пароль». В списке видны тема, текст и время; можно сортировать по дате,
  фильтровать по датам, листать по 50 и удалять.

### 6.3. Логирование на фронтенде

`lib/logger.js` — обёртка над `console` с порогом уровня (`setLevel`). Действия
(отправка отзыва, вход/выход, загрузка страницы, удаление) пишутся на INFO, детали
запросов — на DEBUG, сбои — на WARN/ERROR.

## 7. Nginx (reverse proxy)

Официальный `nginx:alpine` с одним конфигом. Он — единственная публичная точка на
порту 80 и раздаёт по HTTP (без шифрования, по требованию):

- `location /api/` → `http://backend:8080/api/` (префикс `/api` сохраняется);
- `location /` → `http://frontend:80/` (статика SPA).

Поскольку фронтенд обращается к относительному `/api`, всё идёт с одного источника —
CORS в реальной работе не нужен (разрешающий CORS на бэкенде оставлен только для
прямого доступа к `:8080` при тестировании).

## 8. Тестирование

### Backend (`pytest`)

- **unit** — изолированно, без БД: `config`, `logging`, `exceptions` (+ маппинг в
  статусы), `security` (в т.ч. просроченный/поддельный токен), схемы,
  репозитории (на mock-сессии SQLAlchemy) и сервисы (на фейковых репозиториях из
  `conftest.py`).
- **integration** — контроллеры через `TestClient` с подменой зависимостей: успешный
  и неуспешный вход, создание и валидация отзыва, защита списка токеном, удаление и
  `404`. Проверяется в том числе перевод доменных исключений в HTTP.

Запуск:

```bash
cd backend
pip install -r requirements-dev.txt
pytest
```

БД-специфичные пути (`uuidv7()`, `now()`) требуют реального PostgreSQL 18 и проверяются
при запуске стека; в юнит-тестах эти значения подставляют фейки.

### Frontend (`vitest` + Testing Library)

Тесты покрывают утилиты (`logger`, `token`, `datetime`), api-модули (на замоканном
`fetch`), компоненты (`Field`, `Button`, `ErrorBanner`) и страницы (`FeedbackForm`,
`LoginForm`).

```bash
cd frontend
npm install
npm test
```

## 9. Запуск и эксплуатация

```bash
docker compose up --build      # собрать и поднять всё
# открыть http://localhost/
```

Переменные окружения бэкенда задаются в `docker-compose.yml`: `DATABASE_URL`,
`JWT_SECRET`, `JWT_EXPIRE_MINUTES`. Учётки по умолчанию: приложение — `admin` /
`password`; PostgreSQL — роль `admin` / `password`, база `feedback`.

Новые администраторы заводятся вручную через открытый порт 5432 (id проставит БД):

```bash
psql postgresql://admin:password@localhost:5432/feedback \
  -c "INSERT INTO users (login, password) VALUES ('hr_lead', 'секрет');"
```

### Два режима запуска и переносимый слой данных

- **Production (по умолчанию):** `docker compose up --build` — четыре контейнера,
  PostgreSQL 18, схема через Alembic, `id`/время генерируются на стороне БД
  (`uuidv7()`, `now()`).
- **Локально одним процессом:** `./run-local.sh` — FastAPI отдаёт API и собранный SPA
  на SQLite, без Docker; удобно, чтобы быстро увидеть работу.

Код общий. Выбор диалекта происходит по `DATABASE_URL`: фабрики колонок
(`models/columns.py`) на PostgreSQL ставят `server_default` (генерация на стороне БД),
а на прочих движках — прикладной `default` (переносимый тип `GUID` и генератор
`uuid7()` из `core/ids.py`). Так production-требование «генерация на стороне БД»
сохраняется, а локальный запуск не требует PostgreSQL. В локальном режиме схема
создаётся при старте (`create_all`) и заводится админ `admin`/`password`; на
PostgreSQL этот шаг — no-op, схемой владеет Alembic.

---

## 10. Замечания по безопасности

Два решения приняты **намеренно по условию задачи** и допустимы только внутри
доверенной сети: пароли администраторов хранятся открытым текстом (регистрация
вручную через БД), а трафик идёт по HTTP без шифрования. Перед любым расширением
периметра следует добавить хеширование паролей (например, bcrypt) и TLS; менять для
этого нужно ровно один слой — `AuthService` (сверка) и миграцию/провижининг паролей.

## 11. Как расширять

- **Новый эндпоинт:** схема в `schemas/` → метод в сервисе (правило) → при
  необходимости метод в репозитории (доступ к данным) → маршрут в контроллере. Новые
  ошибки — как подкласс в `exceptions.py`, при нужде — новая строка в маппинге
  статусов.
- **Новый экран фронтенда:** api-функция в `api/` → хук в `hooks/` (если есть
  состояние) → компонент/страница. Транспорт и отображение остаются разделены.

## 12. Интеграция с Bitrix24 (справочник сотрудников)

Список авторов для формы берётся из Bitrix24 — там всегда актуальные сотрудники.

Как устроено (по слоям, как и остальной код):
- `integrations/bitrix_client.py` — тонкий клиент к **входящему вебхуку**
  (`https://<портал>/rest/<id>/<код>/<метод>.json`, POST c JSON). Методы:
  `user.get` (активные сотрудники, фильтр `ACTIVE`, пагинация по 50 через
  `start`/`next`/`total`) и `department.get` (названия отделов). Ответ-конверт
  `{result, next, total}`; ошибка Bitrix `{error, error_description}` заворачивается
  в доменную `BitrixError` (→ HTTP 502). Только stdlib (`urllib`) — без новых
  зависимостей.
- `services/employee_service.py` — кэш в памяти с TTL (по умолчанию сутки). Bitrix
  дёргается ~раз в день, а не на каждый заход на форму. Если Bitrix недоступен —
  отдаётся последний удачный кэш; ошибка всплывает только при «холодном» кэше.
- `controllers/employee_controller.py` — `GET /api/employees` (публично, для
  выпадающего списка) и `POST /api/employees/sync` (админ, принудительное
  обновление).

Заглушка и подключение боевого вебхука:
- Если `BITRIX_WEBHOOK_URL` не задан — клиент отдаёт встроенный демо-список
  (`STUB_EMPLOYEES`), приложение работает сразу.
- Чтобы подключить реальный Bitrix: создайте входящий вебхук с правом `user`
  (и `department` для названий отделов) и впишите его базовый URL в `.env`:
  `BITRIX_WEBHOOK_URL=https://<портал>.bitrix24.ru/rest/<id>/<код>/`. Токен живёт
  только на сервере (в `.env`), в клиентский код не попадает. Пример — в
  `backend/.env.example`.

Модель автора у идеи (при реализации подачи) хранит стабильный `author_bitrix_id`
плюс снимок имени/подразделения на момент отправки — чтобы исторические заявки и
недельный зачёт оставались корректными даже после смены отдела или увольнения.
